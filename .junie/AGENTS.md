# AGENTS.md — AI Agent Guidelines for aivillage

## Project Overview

aivillage is a pixel-art village simulation game built with Python and Pygame. It features 19 AI-powered villagers with jobs, voices, and relationships that simulate real life using the actual clock, weather, and news. Dialogue is generated by LLMs (Large Language Models) through a provider-agnostic adapter system.

**Current version:** 0.4.19
**Python version:** 3.11–3.12 (do NOT use 3.13+)
**License:** See LICENSE file

## Architecture

The codebase follows a modular architecture with clear separation of concerns:

### Core Modules

- **`aivillage/app.py`** — Main application class (`VillageApp`) using mixin composition
- **`aivillage/app_*.py`** — Mixins for specific functionality:
  - `app_services.py` — Service initialization
  - `app_visitors.py` — Visitor/traveller handling
  - `app_social.py` — Social interactions
  - `app_persistence.py` — Save/load functionality
  - `app_controls.py` — Input handling
  - `app_loop.py` — Main game loop
- **`aivillage/agents/`** — Villager AI logic (persona, needs, routines, memory, social)
- **`aivillage/llm/`** — LLM client abstraction and provider adapters
- **`aivillage/news/`** — News pipeline (feeds, filters, dispatch, alerts)
- **`aivillage/reality/`** — Real-world integration (clock, weather, geo, calendar)
- **`aivillage/render/`** — Rendering, UI, HUD, dialogs, camera
- **`aivillage/voice/`** — Text-to-speech (pyttsx3/SAPI5)
- **`aivillage/world/`** — World map, landmarks, pathfinding, geometry
- **`aivillage/assets/`** — Fonts, sprites, SFX, palette

### Entry Points

- **`run.py`** — Main launcher script
- **`build_app.py`** — Native desktop build (PyInstaller)
- **`build_installer.py`** — Platform-specific installer generation

## Development Setup

### Environment Setup

```powershell
# Using uv (recommended)
uv venv --python 3.12
.\.venv\Scripts\Activate.ps1
uv pip install -e ".[dev]"

# Or using plain venv
py -3.12 -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -e ".[dev]"
```

### Running the Application

```powershell
python run.py                    # Default launch
python run.py --new              # Fresh village (ignore saves)
python run.py --provider mock    # Offline demo mode
python run.py --lang de          # German interface
python run.py --location Leipzig # Override city detection
```

### Running Tests

```powershell
python -m pytest -q              # Quick run
python -m pytest -v              # Verbose output
python -m pytest tests/test_*.py # Specific test file
```

Tests use dummy SDL video/audio drivers and run headless. 196 tests should pass, 1 skipped.

### Building

```powershell
python build_app.py              # Create native desktop builds
python build_installer.py        # Generate platform installers
```

Or use the batch scripts:
- `Build aivillage.cmd` — Build desktop app
- `Build installer.cmd` — Build installers

## Code Conventions

### Python Style

- **Type hints:** Use modern Python type hints (`list[str]`, `int | None`)
- **Imports:** 
  - Future imports first (`from __future__ import annotations`)
  - Standard library
  - Third-party packages
  - Local imports (use relative imports within packages)
- **Naming:**
  - Modules: `snake_case`
  - Classes: `PascalCase`
  - Functions/variables: `snake_case`
  - Constants: `UPPER_SNAKE_CASE`
- **Docstrings:** Brief one-liners for modules and public functions
- **Line length:** ~100 characters preferred

### Mixin Pattern

The main `VillageApp` class uses mixin composition instead of deep inheritance:
- Each mixin handles one concern (services, visitors, social, etc.)
- Mixins are listed in MRO order in the class definition
- New functionality should be added as mixins, not by modifying existing ones

### Configuration

- Configuration lives in `config.toml` (copy from `config.example.toml`)
- Access via `Config` class in `aivillage/config.py`
- Never hardcode values that should be configurable
- API keys should NEVER be committed — use `.env` file (see `.env.example`)

### Internationalization

- Use `self.i18n.get("key")` for UI strings
- Locale files in `aivillage/locales/*.json`
- Support for English and German

## Testing Guidelines

### Test Structure

- Tests live in `tests/` directory
- Named `test_*.py` following pytest conventions
- Use `conftest.py` for shared fixtures

### Testing Approach

- Unit tests for pure logic (economy, news pipeline, world generation)
- Integration tests for app lifecycle and services
- Mock external dependencies (LLM providers, weather API, news feeds)
- Use `--provider mock` for headless app tests

### When to Add Tests

- **Bug fixes:** Add a reproducer test first, verify it fails, then fix
- **New features:** Add tests proportional to complexity
- **Refactoring:** Rely on existing tests; add only if coverage is missing

## Security Considerations

- **NEVER commit API keys** — use `.env` file (gitignored)
- **NEVER commit save games** — they may contain personal data
- **NEVER commit generated builds** — use CI/CD for builds
- API key environment variable names are stored, not the keys themselves
- Remote LLM gateways should use HTTPS

## Common Gotchas

1. **Python version:** Must use 3.11 or 3.12. Python 3.13+ wheels are not available yet.
2. **Pygame initialization:** Always call `pygame.init()` before other pygame calls.
3. **LLM providers:** The mock provider is for testing only; real dialogue requires a configured provider.
4. **Windows SAPI:** Voice features are Windows-only; handle gracefully on other platforms.
5. **Save slots:** Multiple save slots exist; autosave follows the last saved/loaded slot.
6. **Configuration precedence:** CLI args > setup screen > config.toml > defaults
7. **Mixins order:** Method Resolution Order (MRO) matters in `VillageApp` class definition.

## Workflow Guidance

1. **Before making changes:** Understand the module structure and identify which files are affected.
2. **After making changes:** Run relevant tests to verify nothing is broken.
3. **For visual changes:** Note that visual verification requires manual testing or screenshots.
4. **For LLM-related changes:** Test with `--provider mock` for automated tests.
5. **Update documentation:** If behavior changes, update relevant docs (PROGRESS.md, README.md).
6. **Do not commit:** Unless explicitly asked by the user.
